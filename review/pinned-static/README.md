# 静态贴图的窗口级检查与测量

本目录只保留在个人 fork，排除在拟提交上游的分支之外。

```powershell
dotnet run --project review/pinned-static/PinnedPerf.csproj -c Release -p:EnableSourceControlManagerQueries=false
```

`Program.cs` 直接实例化生产 WPF 窗口，使用固定生成的 800×400 图像和 73 字符段落。窗口在屏幕外显示，不读取桌面、不调用 OCR/翻译服务、不模拟用户操作。它是窗口生命周期和性能微基准，不能替代真实截图调用链的手动验收。

检查内容：已有窗口的内容与 Chrome 均 cloak、重复截图请求不排队、lease 重复释放、截图期间新增/关闭贴图、恢复后的 cloak 状态、关闭后 WeakReference 可回收。

测量前等待首次 WPF/JIT 初始化结束。测量 1、10、30 个窗口，空闲 CPU 每次采样 3 秒，隐藏/恢复每组 5 次取中位数。原始 JSONL 见 `runtime-benchmark.jsonl`。

- 快照复制：1000 次均值约 7.64 微秒，每次托管分配 12032 字节（原文/译文各 73 个字符）。复用冻结位图，不复制像素缓冲区。
- 创建窗口：单窗 134.3 ms；10 窗共 419.9 ms；30 窗共 1310.7 ms。包含 WPF/原生窗口创建；单窗仍有惰性初始化成本。
- 空闲 CPU：本次基线及三组窗口均未采到进程 CPU 时间增长。计时存在分辨率限制，不等于所有机器绝对零占用。
- 内容与 Chrome 隐藏+恢复：中位数约 33.1 / 33.4 / 33.4 ms，包括两次 DWM 同步。
- 创建后的进程私有内存增量：33.5 / 67.3 / 161.1 MiB。包括 WPF/DWM 渲染表面和运行时缓存，不能把它当作精确的每窗常驻内存。托管差值受 GC 影响，可能为负，不据此声称窗口没有内存成本。
- 三组已关闭贴图的 WeakReference 存活数均为 0。

结论：新增选择/快照逻辑轻量，没有空闲重算任务；保留原外观的两个窗口及图片渲染仍有实际内存成本。因此 PR 说明应给出这些边界，不能笼统宣称整个贴图窗口“几乎零开销”。屏幕外测量不覆盖可见桌面上的 GPU 合成和拖动帧率。
